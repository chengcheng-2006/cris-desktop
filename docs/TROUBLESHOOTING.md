# 故障排查

本文针对当前公开 main 的脚本和已知测试结果。优先停止操作、保留错误码并检查输入输出路径；不要通过覆盖应用、删除旧 profile 或上传未脱敏日志来“试试看”。本项目不会要求你把运行 profile、日志、会话或凭据反复贴回 Issue。

## DS Bot 导入时报 `createSystemMessage` 不存在

**症状**：桌面应用启动，但 DS Bot 导入或初始化失败；错误涉及 `createSystemMessage` 缺失，或模块导入失败。

**原因**：当前公开 main 默认安装 `ds-bot@0.2.7`，其依赖解析到旧 peer `dsh-llm@0.0.1-rc.5`；该版本没有 DS Bot 需要的 `createSystemMessage`。这是当前公开代码的已知阻断问题，不是你填写 API key 就能修复的问题。

**建议**：

1. 不要反复重装或改动正在使用的 profile；先退出应用并备份相关数据。
2. 检查正在使用的构建来自哪个仓库提交，不要把其他机器上的修复版本当成公开 main。
3. Mini 上曾有一份本地修复试验，模块依赖解析与移动后解析、严格 ad-hoc 签名检查通过；桌面界面及插件入口验证当时被 Computer Use 访问授权挡住，修复代码也未同步进公开仓库。因此它不是已发布修复，不能据此保证功能可用。
4. 等修复进入公开仓库并有独立端到端验证后，再评估升级。当前文档不提供未经审核的手工替换步骤。

若要报告新证据，只需提供可公开的仓库提交号、依赖版本和脱敏后的错误类别；不要附完整日志、profile、用户名路径、token 或会话正文。

## 构建脚本退出非零

- 在独立 Bash 块中启用 `set -euo pipefail`，避免失败后继续或由 `tee` 掩盖错误；pipefail 的结果是最右侧失败命令的状态，不一定是构建脚本的原始退出码。
- 核对 `--src-app` 指向真实的 `.app`，且其内部存在 `Contents/Resources/app` 和脚本所需 patch 文件。
- 核对 `--out` 是仓库外的专用目录，且输入应用不等于 `$OUT/Cris.app`（或 `--name` 指定的目标）。脚本会先删除同名目标。
- 若提示依赖安装错误，默认模式需要 npm 和 registry 网络访问。可选覆盖目录必须同时存在 `ds-bot/`、`deep-view/`；脚本不核验其版本和完整性。
- 不要将整个构建日志直接发到公开 Issue。若需报告，请先本机筛除绝对路径、用户名、密钥、访问令牌和运行配置，只发最小相关错误上下文。

完整的输入结构与清理行为见[构建说明](BUILD.md)。

## `hdiutil` 报“目录非空”、挂载失败或 DMG 创建失败

脚本会处理旧的同名挂载和镜像残留，但它可能尝试强制卸载 `/Volumes/<应用名>`，而且也会清理输出目录中的同名 DMG、app 和临时 staging。先确认没有其他工作正在使用该卷，并为构建选择一个新的仓库外输出目录。

检查当前挂载状态：

```bash
mount | grep '/Volumes/'
hdiutil info
```

不要不加判断就强制卸载共享卷或删除目录。如果看到应用名相同但由其他任务使用的挂载，停止构建并先确认其用途。运行前检查 `--name`、输出目录以及其内的同名文件；脚本不能判断文件是否对你重要。

## 验收脚本 PASS，但应用或插件不可用

`verify-artifact.sh` 只检查有限的文件结构、模板声明、部分更新入口和签名状态记录。它不做严格签名验证，不证明 DS Bot 能导入、不证明桌面 UI/插件入口正常、不证明模型能响应，也不验证已有 profile 的迁移。

若结构检查通过但应用功能失败，先按“DS Bot 导入时报 `createSystemMessage` 不存在”处理，并保留产物与仓库提交的对应关系。可单独执行严格签名检查：

```bash
codesign --verify --deep --strict --verbose=2 "${INSTALLED_APP:?先设置本次实际检查的应用路径}"
```

以命令的实际退出码和诊断为准。脚本自身只尝试 ad-hoc 签名；签名失败仅 WARN 并继续。strict 检查成功也不能把 ad-hoc 签名变成 Developer ID 签名或 Apple 公证。

## 首次启动没有模板、或已有 profile 表现异常

构建脚本修改上游初始化逻辑以尝试复制资源模板，但复制异常会被捕获并忽略。仓库没有证明以下行为完整可靠：

- 对已有 profile 自动迁移或修复旧依赖；
- 覆盖 profile 时保留所有用户数据；
- 多 profile、并行启动或升级过程的隔离与回滚；
- 把 Mini 本地修复与 UI 行为推广到所有用户环境。

不要直接删除、替换或覆盖旧 profile，也不要把旧 profile 全目录复制到模板。先退出对应应用并制作本机备份，优先在独立 macOS 测试账户或虚拟机复现；其他方案须先核实完整启动隔离。仅新建 profile 或改名不足以保护旧 Electron 状态。无法确认时停在静态检查，不打开应用。若仍无法启动，停止试验；分享时只提供版本/提交、失败阶段和脱敏错误类别，不上传 profile、会话、数据库或完整日志。

## 上游 DMG 摘要不匹配

预期 SHA-256 为入门指南中记录的值。用 `shasum -a 256 <DMG路径>` 计算并逐字比较；任何不一致都停止，不要挂载或运行下载文件。不要通过忽略错误或改写期望摘要来继续。

## Gatekeeper 阻止打开

当前构建尝试 ad-hoc 签名，失败可只告警；DMG 未签名、未公证。先满足[入门指南](GETTING_STARTED.md#首次启动与隔离条件)的启动隔离条件，并对最终安装副本严格验签。之后才考虑 Finder 中右键选择“打开”。只有确认来源可信且核对实际安装对象时才考虑移除 `com.apple.quarantine`，该操作不能修复失效签名；具体命令见[入门指南](GETTING_STARTED.md#gatekeeper-签名与公证)。不要对来历不明的应用移除隔离标记。公众分发需要 Developer ID 正式签名和 Apple 公证，当前仓库未提供。
